# Configuration

`yeah` is configured through environment variables, read from the `.env` file in the repository root (`/opt/yeah/.env` on a production install). `.env.example` is the annotated reference; the installer generates a working `.env` for you.

## Core variables

| Variable | Default | Purpose |
|---|---|---|
| `DATABASE_URL` | — | Postgres connection string |
| `REDIS_URL` | — | Redis connection string (BullMQ and pub/sub) |
| `SESSION_SECRET` | — | Signs sessions and OAuth state. Use a long random value in production |
| `ENCRYPTION_KEY` | — (generated by the installer) | AES-256-GCM key for secrets at rest. **Required in production — back it up** |
| `ENCRYPTION_KEY_PREVIOUS` | empty | Old keys (comma-separated) still accepted for reading during rotation; then run `db:rekey` |
| `API_PORT` / `WS_PORT` / `WEB_PORT` | 3000 / 3001 / generated | Service ports |
| `WEB_ORIGIN` | dev ports | Comma-separated origins allowed to call the API with credentials; also checked against the `Origin` of WebSocket upgrades by `ws`, used for the GitHub App callback URL and as the WebAuthn origin for passkeys. Set it to the real panel URL |
| `PANEL_PATH` | empty | Optional secret path for the dashboard (see [architecture.md](architecture.md#panel_path-an-optional-secret-path)) |
| `VITE_API_URL` / `VITE_WS_URL` | empty in production | Only needed when `api` / `ws` run on a different host or port than the dashboard |
| `WEB_BIND` | `0.0.0.0` | Host address the dashboard port is bound to (`127.0.0.1` with a tunnel) |

## Optional integrations

| Variable | Purpose |
|---|---|
| `GITHUB_APP_ID`, `GITHUB_APP_SLUG`, `GITHUB_APP_PRIVATE_KEY_BASE64`, `GITHUB_APP_WEBHOOK_SECRET` | Enable the GitHub App integration (auto-deploy on push, previews). `.env.example` has the registration walkthrough |
| `LOCALHOST_SSH_PRIVATE_KEY_BASE64`, `LOCALHOST_SSH_HOST`, `LOCALHOST_SSH_PORT`, `LOCALHOST_SSH_USER` | Register the panel's own machine as the first deploy server (written by the installer outside control-plane-only mode) |
| `COMPOSE_PROFILES=tunnel`, `CLOUDFLARE_TUNNEL_TOKEN`, `TRUST_CF_CONNECTING_IP` | Expose the panel through a Cloudflare Tunnel |

## Operational tuning

All optional; empty means the default.

| Variable | Default | Purpose |
|---|---|---|
| `METRICS_INTERVAL_SECONDS` | 60 (minimum 15) | Server metrics collection interval. Raising it reduces SSH traffic and CPU when many servers are connected |
| `PATCH_CHECK_INTERVAL_SECONDS` | 21600 (6 h, minimum 600) | How often the worker checks each connected server for OS updates (`apt`) |
| `LOG_RETENTION_DAYS` | 90 | Days until the text log of finished deployments, backups, tasks, cleanups and updates is cleared (history stays). `0` disables |
| `AUDIT_RETENTION_DAYS` | 365 | How long the audit log is kept. `0` keeps it forever |
| `DB_POOL_MAX` | Bun default (6 in `docker-compose.prod.yml`) | Maximum Postgres pool size per process (`api`, `worker`, `ws`). The production compose uses 6, so the panel holds at most about 18 connections against `max_connections=50` |
| `FILE_BROWSER_WRITES` | `false` | Allows changing files from the container file browser (save, upload, create folder, delete). Reading is always allowed. See [security.md](security.md#container-file-browser-writes) |
| `FILE_BROWSER_UPLOAD_MAX_MB` | 10 (1 to 100) | Largest file the file browser accepts as an upload |
| `LOG_FORMAT` | `json` | `json` (one JSON line per event) or `text` |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn` or `error` |

## Running on little memory

The panel is designed to fit a small machine (for example a 1 vCPU / 4 GB VPS). There is no resident agent on the managed servers: metrics, traffic and cleanup use ephemeral SSH connections.

Memory limits already applied in `docker-compose.prod.yml`:

| Service | Maximum memory |
|---|---|
| postgres | 384 MB (`POSTGRES_MEMORY_LIMIT`), started with `shared_buffers=64MB` (`POSTGRES_SHARED_BUFFERS`) and `max_connections=50` |
| redis | 192 MB (`maxmemory 128mb`) |
| api | 384 MB |
| worker | 512 MB |
| ws | 128 MB |
| web | 64 MB |
| cloudflared (optional) | 96 MB |

That adds up to about 1.5 GB in the worst case (a fraction of that in practice), leaving the rest of the machine to your apps if it is also a deploy server.

For the full picture of a 1 vCPU / 4 GB server running many projects (memory budget, limits, sleep, the memory guard, disk), see [small-server.md](small-server.md).

Levers to squeeze further:

- Raise `METRICS_INTERVAL_SECONDS` and `PATCH_CHECK_INTERVAL_SECONDS`.
- Turn monitoring off per server: server *General* tab → "Monitoring".
- The custom error page is opt-in per server (the *Proxy* tab): optional title and message, shown for unknown domains and for 502/503/504. Saving restarts the proxy briefly. Maintenance mode for services and stacks is on the service's *General* tab.
- Traffic analytics is opt-in per server (the *Proxy* tab) and costs one local read of Traefik every 5 minutes.
- Use `LOG_LEVEL=warn` for less log output.
- Install the panel on another machine (`--control-plane-only`): Postgres, Redis, the API and the worker then leave the apps' VPS.
